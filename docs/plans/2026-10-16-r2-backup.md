# Private R2 backup receiver implementation plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Keep one independently verified encrypted offsite recovery point without requiring two full archives on the receiver disk.

**Architecture:** Retain the existing upload-only SSH boundary and stream_v2 framing. An explicitly enabled receiver uses the official S3 SDK to put ciphertext into a dedicated private R2 bucket. The producer receives no R2 credentials, read/list/delete endpoint or retention controls. Local root maintenance promotes only an independently restored candidate before deleting exact superseded objects.

**Tech stack:** Python, boto3 (receiver-only locked dependency), R2 Standard, existing age bundles and independent restore proof format.

## Context and constraints

P1: How must encrypted delivery preserve producer confinement and snapshot identity? Tiden lookup 2026-10-16 matched specs 123, 125, 126, 127; use the current stream_v2 protocol, not a new provider-facing API. No provider sessions, plaintext or production credentials enter synthetic tests.

P2: How does one-point retention preserve a verified recovery point? The same lookup matched specs 120, 121 and 128. Upload success never proves recoverability. Old and new points coexist temporarily. Root-owned proof/control files, exact identities, a durable pending rotation journal and compare-and-swap marker are required. Initial enrollment is explicit; it never deletes anything.

Current filesystem receiver and sender behavior stay compatible. Never mount an object store as a POSIX filesystem. Never interpret multipart ETags as full SHA256. No public access or age-based deletion of committed archives. An uncertain storage write must never authorize an overwrite or deletion. Keep concrete operational receipts private. Installing/applying on hosts follows verified main and CI.

## Task 1: Constrained R2 configuration and SDK boundary

Files: create `services/messaging/messaging_service/backup_r2_receiver.py`, `tests/test_backup_r2.py`, `services/messaging/requirements-backup-r2.in` and its pinned lock.

3. Add a lazy official boto3 client factory; no SDK import or credential resolution on normal application imports. Explicit credentials only, no ambient AWS or instance metadata fallback. No secret values in errors/logs. Use signature v4, region auto, bounded timeouts/retries and supported checksum behavior.
4. Run the tests. Keep the SDK dependency off default application images and dependencies.

## Task 2: Append-only stream_v2 delivery

Files: same module and tests; existing `backup_receiver.py` may only receive small pure helper extraction if needed and fully regression-tested.

1. Write failing synthetic framed stream tests for normal multipart delivery, duplicate same snapshot, conflicting ID, truncated/oversized data, invalid age prefix/footer/EOF, failure before encoder confirmation, quota, concurrent receiver lock and storage errors.
2. Implement the same wire ready/stored receipts as `backup_runner.upload_stream`. Accept only v2 for this opt-in backend. Buffer bounded equal-size S3 parts (at least 5 MiB except final). Only complete multipart after the entire input, footer, hash, age prefix and EOF are validated.
3. Give each attempt a random immutable physical ciphertext key. Publish a bounded logical receipt under a deterministic backup ID using atomic `PutObject(IfNoneMatch='*')`; the receipt binds the actual physical object key, size, SHA256 and snapshot SHA256. Competing publications can never overwrite a committed ID. A logical retry returns only an internally verified matching committed receipt. The outward wire receipt need not expose the physical key.
4. Persist a private local journal before uncertain writes. Pre-completion failed parts may be aborted; a completion with unknown outcome retains evidence and never starts a replacing attempt based on one negative HEAD. Conditional receipt publication may retry the exact same body safely. On recovery, reconcile only that exact attempt. Bound committed plus orphan object usage and allow at most two full archive objects; unresolved candidates block further accumulation. Never delete a committed previous point on upload. Clean up only exact unpublished owned attempt resources when their status is certain.
5. Test dropped responses after complete and receipt publication, SDK errors versus genuine not-found, corruption, conflicting logical receipts, and recovery without a second capture.

## Task 3: Operator download and verified one-point rotation

Files: same module and tests, root proof validation may reuse pure helpers from the filesystem receiver.

1. Write failing tests for hash-verified atomic download, explicit first enrollment, exact seven-check restore proof validation, stale marker, wrong snapshot/body/proof, root ownership and symlink/hardlink/ancestor attacks, shared receiver lock, interruption before/after marker switch, idempotent same-proof retry, unrelated pending objects and no sender-selected maintenance.
2. Implement a local operator download into a private regular temporary file, full SHA256/size verification then atomic publication. No decryption key is placed on the receiver.
3. Implement root-only initial protect (requires absent marker and independently restored cloud object, deletes nothing) and root-only rotate with exact prior marker digest. Reuse the established independent proof shape, requiring matching committed receipt identity and full object hash. Fsync a root-owned rotation journal, switch/fsync the local trusted marker, then delete only the exact verified superseded object's physical key and logical receipt. Recheck the new protected point on resume before any further deletion. Unknown remote delete outcomes remain recoverable under the same journal.
4. Keep maintenance argv separate from the SSH forced-command entry point. Standard receive must never interpret SSH_ORIGINAL_COMMAND or accept proof/control paths from stdin.
5. Run new tests plus existing filesystem receiver/streaming/anchor regressions. No production data or cloud credentials in the tests.

## External gates

The user activates the R2 subscription/terms or confirms the specific browser action. Credential creation requires confirmation at the actual browser action, with one private bucket and least necessary Object Read & Write scope. Keep secret keys out of chat/Git. User login and payment are not synthetic acceptance evidence. A fresh compatible production snapshot and actual quarantined restore remain release gates.
